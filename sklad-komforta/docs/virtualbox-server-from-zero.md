# С нуля: VirtualBox, Ubuntu Server, Cloudflare и Windows-клиент

Инструкция для владельца «Склада Комфорта». Проверена по структуре проекта
11.10.2026. Это руководство, не отчёт о состоявшемся публичном развёртывании.
Сервер пока не настроен инструментами этой задачи, домен не зарегистрирован,
установщик не собран, коммиты и ветки не создавались.

## 1. Что получится и где остановиться

Схема:

```text
Пользователь: браузер или приложение Windows
                  |
           HTTPS + ваш домен
                  |
           Cloudflare Tunnel
                  |
Windows-ПК -> VirtualBox -> Ubuntu Server
                             |
                        Nginx / API
                             |
                     PostgreSQL / Redis / S3
```

Cloudflare не хранит сервер приложения вместо вас. Выключение ПК, сон Windows,
остановка ВМ, отключение электричества или домашнего интернета делают сервис
недоступным. Для первых пользователей такой вариант возможен, но это один узел
без отказоустойчивости. Для постоянной работы разумно позже перенести сервер
на VPS/выделенный компьютер. Уже сейчас резервные копии должны находиться
не только на диске этого ПК.

**Можно выполнять сейчас: этапы 2–6.** После них получится ВМ с Docker.
Все команды можно вводить прямо в консоли VirtualBox: SSH не обязателен.
Этапы 7–14 описывают последующий порядок и контрольные точки.

**Для одной ВМ подготовлен `compose.server.yaml`.** Существующий
`compose.production.yaml` требует внешних PostgreSQL, Redis, S3 и файлов TLS.
Он НЕ создаёт все хранилища на одной новой ВМ и НЕ настраивает Tunnel.
Команды серверного профиля приведены в
[инструкции запуска одной ВМ](iteration-08/server-deployment.md).
Сценарий Windows-установщика остаётся отдельным следующим этапом.
Не публикуйте вместо него обычный `compose.yaml`: это среда разработки
с Development-настройками, Mailpit и опубликованными служебными портами.

## 2. Подготовить виртуальную машину

На Windows в VirtualBox:

1. Создать ВМ `SkladKomforta-Production`.
2. Выбрать скачанный официальный ISO Ubuntu Server 26.04.1 amd64.
3. Выбрать Linux / Ubuntu 64-bit. Если предлагается автоматическая установка,
   для этой инструкции пропустить её и пройти установку вручную.
4. Начальная оценка ресурсов: 4 виртуальных CPU, 8 ГБ RAM, диск 100 ГБ VDI
   с динамическим выделением. Это ориентир, не гарантия производительности.
   Не отдавать ВМ все ресурсы ПК. Если у ПК всего 8 ГБ RAM, сначала согласовать
   меньшую конфигурацию; серверная сборка Flutter/.NET потребляет заметную память.
5. Диск ВМ хранить на SSD с достаточным свободным местом. Динамический диск
   всё равно может вырасти до установленного максимума.
6. Сеть, адаптер 1: **NAT**, кабель подключён. Сетевой мост не требуется.
7. Если работаете прямо в консоли ВМ, **проброс портов не нужен**.
   Только для необязательного SSH из Windows можно добавить:

| Имя | Протокол | IP хоста | Порт хоста | IP гостя | Порт гостя |
|---|---|---|---|---|---|
| SSH | TCP | 127.0.0.1 | 2222 | пусто | 22 |

Адрес 127.0.0.1 обязателен: SSH будет доступен только с этого Windows-ПК,
а не со всех сетевых интерфейсов. Порт 2222 должен быть свободен.
Не пробрасывать 5432, 6379, 8080, 9000 или 9001. На роутере ничего не открывать.
Такой NAT-проброс поддерживается VirtualBox: [руководство Oracle](https://docs.oracle.com/cd/F22853_01/F22854/F22854.pdf).

## 3. Установить Ubuntu Server

1. Запустить ВМ и установщик Ubuntu Server.
2. Выбрать язык/клавиатуру. Сервер можно установить на английском;
   русский интерфейс приложения от этого не изменится.
3. Для сети оставить DHCP на виртуальном NAT-адаптере.
4. HTTP proxy оставить пустым, если в вашей сети его нет.
5. Для диска выбрать созданный виртуальный диск ВМ. Перед подтверждением
   проверить размер: установка стирает выбранный диск. Физические диски
   Windows подключать к ВМ для этой установки не нужно.
6. Если используется LVM, проверить, сколько места реально выделяется `/`:
   весь виртуальный диск не всегда автоматически отводится корневому разделу.
7. Имя сервера: `sklad-prod`. Имя пользователя для примеров: `skladadmin`.
   Задать уникальный сильный пароль и сохранить его в менеджере паролей.
8. **Install OpenSSH server** можно не включать. Для работы прямо в ВМ он не нужен.
9. Дополнительные серверные пакеты/Snap-приложения пока не выбирать.
10. Завершить установку, извлечь ISO из виртуального привода и перезагрузить ВМ.

Если Ubuntu уже установлена, переустанавливать её не нужно: перейти к проверкам.
[Официальная инструкция Ubuntu](https://ubuntu.com/server/docs/basic-installation/).

## 4. Необязательно: подключиться из Windows

Если работаете прямо в VirtualBox и SSH не устанавливали, пропустите весь раздел.

Открыть PowerShell на Windows:

```powershell
ssh -p 2222 skladadmin@127.0.0.1
```

При первом подключении SSH покажет отпечаток ключа сервера. Его можно сверить
в консоли самой ВМ командой:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Пароль при вводе в SSH не отображается — это нормально.
Если соединение отклоняется, в консоли ВМ проверить:

```bash
sudo systemctl status ssh --no-pager
ip -br address
```

При отсутствии SSH установить `sudo apt install openssh-server`.
Не удалять запись известного ключа при неожиданной смене отпечатка,
пока не выяснена причина; после намеренной переустановки ВМ ключ действительно меняется.

## 5. Обновить и проверить сервер

Следующие команды выполнять **в консоли Ubuntu-ВМ** (либо по SSH), не в PowerShell:

```bash
cat /etc/os-release
uname -m
free -h
df -h /
sudo apt update
sudo apt upgrade -y
sudo apt install -y ca-certificates curl git openssl jq ufw python3 gnupg
timedatectl
sudo timedatectl set-ntp true
sudo ufw enable
sudo ufw status verbose
```

Если SSH установлен и вы его используете, ДО `sudo ufw enable` выполните
`sudo ufw allow OpenSSH`. Без SSH этот шаг не нужен. Оставить доступ к консоли
VirtualBox на случай ошибки. При использовании SSH проверить второе подключение.
Не отключать вход по паролю, пока вход по SSH-ключу не настроен и не проверен.
Правильное время важно для TOTP и срока действия токенов.

Если после обновления требуется перезагрузка:

```bash
test -f /var/run/reboot-required && cat /var/run/reboot-required
sudo reboot
```

Подключиться снова после загрузки. В Windows отключить автоматический сон
на время работы сервера. Перезагрузки Windows планировать как простой сервиса.
Для начала запускать ВМ вручную; автозапуск после включения ПК настроить
и проверить отдельно до выдачи доступа постоянным пользователям.

## 6. Установить Docker Engine

Docker официально поддерживает Ubuntu 26.04 LTS. Для production используется
пакетный репозиторий, а не случайный скрипт `curl | sh`.
[Источник и актуальные команды](https://docs.docker.com/engine/install/ubuntu/).

На чистой Ubuntu, где Docker ещё не установлен:

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker run --rm hello-world
sudo docker compose version
```

Если Docker уже был установлен другим способом, сначала проверить пакетную
конфигурацию, а не смешивать установки. Команды в руководстве используют `sudo`:
не требуется добавлять пользователя в группу docker, которая даёт практически
root-доступ. Публикация портов Docker может обходить правила UFW; поэтому
служебные сервисы должны быть закрыты в самой Compose-конфигурации.

**Контрольная точка:** Ubuntu загрузилась, её консоль доступна, Docker выводит
`Hello from Docker!`, Compose показывает версию. На этом можно остановиться
и передать результаты для подготовки следующего этапа. Пароли не присылать.

## 7. Домен и постоянный адрес

Для выбранной схемы с постоянным публичным Tunnel нужен собственный домен
в Cloudflare. Одного аккаунта недостаточно. Покупать домен именно у Cloudflare
не обязательно: можно использовать другого регистратора и DNS Cloudflare.
[Требования Cloudflare](https://developers.cloudflare.com/tunnel/get-started/).

1. Выбрать и зарегистрировать домен. До оплаты проверить цену продления,
   а не только первого года. Конкретное имя выбирает владелец.
2. Добавить домен в Cloudflare.
3. Если домен куплен у другого регистратора, заменить nameservers на те,
   которые Cloudflare показал именно для вашего домена.
4. Дождаться состояния Active. Существующие DNS-записи другого сайта/почты,
   если они есть, предварительно сохранить и не удалять вслепую.
5. Предлагаемые имена: `app.ВАШ-ДОМЕН` для сайта и API,
   `files.ВАШ-ДОМЕН` для подписанных ссылок файлов, позднее
   `test.ВАШ-ДОМЕН` и `files-test.ВАШ-ДОМЕН` для отдельного стенда.

`example.com` в документации — заглушка, не ваш адрес.
`trycloudflare.com` годится для временной демонстрации, но не для адреса,
встроенного в установщик. [Назначение Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).

## 8. Подготовить профиль проекта для одной ВМ

Профиль уже подготовлен в `compose.server.yaml`, шаблон переменных находится в
`.env.server.example`, административные команды — в `scripts/server.py`.
Обычный `compose.yaml` и профиль внешних хранилищ не изменяются.
После переноса кода выполняйте точные команды из
[инструкции одной ВМ](iteration-08/server-deployment.md).

Состав серверного профиля:

| Часть | Требование |
|---|---|
| API, worker | Production-окружение, собственные секреты, без опубликованного API-порта |
| PostgreSQL | Новый volume, миграции `migrations/public`, без внешнего порта |
| Redis | Пароль, внутренний адрес, отдельный volume, без внешнего порта |
| S3-совместимое хранилище | Новый приватный bucket, постоянный volume, отдельный пользователь приложения с ограниченными правами |
| Web/Nginx | Production-сборка Flutter, `/api/v1` на том же домене, WebSocket, корректный HTTPS forwarded-header |
| Tunnel | Автозапуск, секретный токен, доступ только к нужным публичным сервисам |
| Файлы | Публичный HTTPS endpoint подписанных ссылок, CORS только для нужного сайта, без публичной консоли хранения |
| Эксплуатация | Ограничение размера логов, healthchecks, резервное копирование и проверка восстановления |

Встроенный в проект S3-клиент подписывает URL для отдельного `PublicUrl`.
Поэтому опубликовать только HTML недостаточно: изображения и счета должны
открываться по рабочему HTTPS-адресу файлов. Bucket остаётся приватным,
публикуется S3 endpoint для запросов с подписью, не административная консоль.
Не менять Host/путь/query подписанной ссылки и не включать её публичное кэширование.

Не подключать development Nginx к Tunnel без проверки: он передаёт
`X-Forwarded-Proto=$scheme`. На внутреннем HTTP-участке это даст `http`,
хотя клиент подключился по HTTPS. Нужно доверять заголовкам только от своего
прокси, передавать наружную HTTPS-схему корректно и проверить Secure-cookie.
Не отключать проверку TLS как способ скрыть ошибки конфигурации.

У подготовленного профиля вообще нет опубликованных Docker-портов.
Используется только контейнерный cloudflared: оба маршрута идут на `http://web:80`.
Не устанавливайте параллельно системную службу cloudflared и не заменяйте
`web` на `localhost`: внутри connector это другой контейнер.

## 9. Передать код без тестовых данных

Корень Git-репозитория — `htdocs`, а новый проект находится в `sklad-komforta`.
GitHub origin: `https://github.com/anasta958-blip/prog.git`.
Сейчас ветка `main`; локальные незафиксированные правки не появятся при clone.
Перед переносом нужен отдельный согласованный релизный коммит и тег.
Не выполнять `git add .`: в репозитории есть и другие файлы/старый проект.
Секреты, дампы, токены, build-кеши и старые данные в коммит не включать.

После согласованной публикации релиза, в Ubuntu:

```bash
mkdir -p ~/apps
cd ~/apps
git clone https://github.com/anasta958-blip/prog.git
cd prog
git fetch --tags
git tag --list
```

Для приватного репозитория использовать отдельный read-only deploy key или
учётные данные GitHub с минимальным доступом. Не вставлять токен в URL clone.
Не копировать на сервер личный приватный SSH-ключ с Windows.

Выбрать согласованный существующий тег, например `v1.0.0`, только после его
создания и проверки. Пример последующих команд:

```bash
git switch --detach v1.0.0
cd sklad-komforta
```

Тег здесь пример, а не утверждение, что он уже существует. На сервер не
копируются `.env` разработчика, дампы PostgreSQL и локальные Docker volumes.

## 10. Секреты и создание чистой базы

В каталоге `sklad-komforta` выполнить (домены заменить своими):

```bash
sudo python3 scripts/server.py init --app-domain app.example.com --files-domain files.example.com
sudo python3 scripts/server.py config
sudo python3 scripts/server.py up
sudo python3 scripts/server.py status
```

`init` создаёт `.env.server` с независимыми секретами и правами 0600,
не перезаписывая существующий файл. `up` собирает приложение и запускает
хранилища, но не Tunnel. Не публиковать полный `docker compose config`:
он раскрывает секреты. Подробности и диагностика — в
[серверной инструкции](iteration-08/server-deployment.md).
Ключ TOTP нельзя заменять при обновлении: он нужен для расшифровки сохранённых секретов.

Порядок первого запуска после проверки профиля:

1. Создать новые volumes именно production-проекта, не подключая development.
2. Запустить PostgreSQL, Redis и файловое хранилище.
3. Дождаться healthchecks. Новый PostgreSQL применяет пронумерованные
   `migrations/public/*.sql` на пустом data-volume.
4. Создать приватный bucket и пользователя приложения; проверить права.
5. Собрать/запустить API, worker и web.
6. Проверить `/health/live`, `/health/ready`, `/api/v1` через внутренний web.
7. Проверить, что нет тестовых пользователей, организаций и карточек.

Public-миграции автоматически выполняются entrypoint PostgreSQL только при
первой инициализации пустого volume. Перезапуск не обновляет существующую БД.
Tenant-схему не создавать вручную: она создаётся приложением при создании
организации с применением tenant-миграций. «Чистая база» здесь означает
пустые рабочие данные и новую схему, а не перенос очищенного рабочего дампа.
Для будущих обновлений необходим отдельный проверенный порядок миграций.

Никогда не применять `docker compose down -v` для «обновления»:
эта команда удаляет volumes и может уничтожить данные.

## 11. Настроить Cloudflare Tunnel

После внутреннего запуска и создания директора:

1. В Cloudflare найти раздел Tunnels (расположение в интерфейсе может меняться).
2. Создать постоянный tunnel, например `sklad-production`, типа cloudflared.
3. Ввести токен через `sudo python3 scripts/server.py set-tunnel`.
   Connector уже описан в Compose; отдельную systemd-службу не устанавливать.
4. Добавить два published application routes: `app.ВАШ-ДОМЕН` и
   `files.ВАШ-ДОМЕН`, оба с service `http://web:80`. Host header не переопределять.
5. Выполнить `sudo python3 scripts/server.py publish`, подтвердив домен.
6. Проверить состояние Healthy/Connected. Токен не публиковать в Git/скриншотах.
7. Проверить оба домена по HTTPS, в том числе подписанные ссылки файлов.
8. DNS для tunnel создавать через Cloudflare, а не A-записью на домашний IP.
9. Проверить HTTPS и отсутствие циклических перенаправлений.

Для контейнера диагностика:

```bash
sudo python3 scripts/server.py status
sudo docker compose --env-file .env.server -f compose.server.yaml --profile public logs --tail 50 cloudflared
```

Не публиковать журналы без удаления чувствительных значений.
Пользователям не нужны Cloudflare-аккаунт, WARP или доступ к VirtualBox.
Не включать автоматически дополнительный интерактивный Cloudflare Access
перед API и подписанными файлами: без отдельной интеграции он может заблокировать
нативный клиент. Основной вход остаётся через авторизацию приложения.
Не включать кэширование API, auth и приватных подписанных файлов.

[Установка connector](https://developers.cloudflare.com/tunnel/downloads/),
[настройка маршрутов](https://developers.cloudflare.com/tunnel/concepts/routing/).

## 12. Первый директор и организация

У приложения нет открытой регистрации. В коде есть закрытый
`POST /api/v1/auth/bootstrap/director`, заголовок `X-Bootstrap-Token`.
Тело содержит `login`, `displayName`, `temporaryPassword`, `employeeLimit`.
По умолчанию лимит сотрудников равен 5; нужное значение согласовать заранее.

Bootstrap выполнять из доверенной внутренней среды до публичного открытия,
не пересылать секреты в чат и не записывать пароль в общедоступный shell-скрипт.
Для этого подготовлена команда `sudo python3 scripts/server.py bootstrap`.
Она спрашивает логин, имя, лимит и пароль; секреты передаются через stdin,
не через аргументы команды. Публичный Nginx блокирует bootstrap-маршрут,
а сам API остаётся закрытым снаружи. Не запускайте bootstrap повторно для того же логина.

Далее в браузере:

1. Открыть `https://app.ВАШ-ДОМЕН`.
2. Войти созданным логином и временным паролем.
3. Сменить временный пароль.
4. Подключить TOTP в приложении-аутентификаторе.
5. Сохранить recovery-коды в безопасном месте, не в единственной ВМ.
6. Создать новую организацию и пройти её настройку.
7. Настроить юрлицо, роли, канбаны, каталог и сотрудников.

Рабочая организация будет чистой. Создание временных тестовых карточек для
приёмки согласовать отдельно либо выполнить на отдельном staging-стенде.

## 13. Проверка, резервные копии и доступ пользователей

До выдачи доступа проверить с другого устройства через мобильный интернет:

- Вход, TOTP, выход и повторный вход после обновления страницы.
- Ссылку клиента КП, включая `?quoteAccessToken=`, без случайной защиты чужим login.
- Изображения каталога, загрузку/открытие счёта PDF, печать и скачивание.
- Импорт/экспорт и размеры реально используемых файлов; лимиты Nginx,
  приложения и Cloudflare должны быть согласованы.
- Изменения в двух одновременно открытых клиентах через WebSocket.
- Сохранность данных после перезапуска ВМ.
- Недоступность из интернета БД, Redis, API-порта, console хранилища и bootstrap.

Резервная копия включает PostgreSQL, файлы S3, секреты шифрования и конфигурацию.
Одного `pg_dump` недостаточно, если документы лежат в отдельном хранилище.
Запланировать ежедневное резервирование с контролем успеха, хранение вне этого
Windows-ПК и несколько поколений копий. Перед релизом/миграцией — отдельная копия.

Для согласованной копии остановить запись приложения и worker либо использовать
проверенную схему согласованных snapshots/backup. Восстановить копию в отдельную
тестовую среду и проверить вход, PDF и изображения. Не проверять восстановление
поверх единственной рабочей базы. Snapshot VirtualBox не заменяет внешнюю копию.

## 14. Windows-приложение и установщик

Сборку Windows выполнять на Windows, не в Ubuntu-ВМ. В проекте нет готового
сценария установщика; его нужно подготовить и проверить отдельно.

1. На Windows разработчика установить Flutter и Visual Studio с компонентом
   **Desktop development with C++**. VS Code не заменяет Visual Studio toolchain.
2. Проверить `flutter doctor -v` и ошибки именно Windows toolchain.
3. Использовать тот же согласованный релизный коммит, что на сервере.
4. Собирать только после выбора постоянного домена.

PowerShell из каталога `sklad-komforta/src/flutter`:

```powershell
flutter pub get
flutter doctor -v
flutter build windows --release --dart-define=API_BASE_URL=https://app.ВАШ-ДОМЕН/api/v1 --dart-define=PUBLIC_APP_BASE_URL=https://app.ВАШ-ДОМЕН --dart-define=APP_ENVIRONMENT=production
```

`ВАШ-ДОМЕН` заменить настоящим ASCII-доменом/его корректным DNS-представлением.
Полная сборка находится в `build/windows/x64/runner/Release` для x64.
Основной файл проекта — `sklad_komforta_app.exe`. Пользователю нужны также
соседние DLL и папка data: одного EXE недостаточно.
[Документация Flutter](https://docs.flutter.dev/deployment/windows).

Для обычного скачиваемого установщика подходит Inno Setup:

1. Подготовить `.iss` с русским названием, версией и постоянным AppId.
2. Включить всё содержимое Release рекурсивно, без исходников и секретов.
3. Установка для текущего пользователя: `{localappdata}\Programs\SkladKomforta`,
   `PrivilegesRequired=lowest`; общесистемную установку согласовать отдельно.
4. Создать ярлык меню «Пуск», при необходимости ярлык рабочего стола и удаление.
5. Предусмотреть C++ runtime: приложение должно работать на чистой Windows,
   где нет Visual Studio. Вариант prerequisite/app-local зависит от состава
   сборки; его нужно проверить, а не считать установленным у всех пользователей.
6. Подписать приложение и установщик при наличии подходящего code-signing
   сертификата. Без подписи Windows может показывать предупреждения;
   наличие подписи также не гарантирует отсутствие всех предупреждений SmartScreen.
7. Проверить установку, вход, PDF, обновление поверх прошлой версии и удаление
   под обычной учётной записью на чистой Windows.
8. Разместить установщик с версией, SHA-256 и описанием изменений.

[Права установки Inno Setup](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm),
[постоянный AppId](https://jrsoftware.org/ishelp/topic_setup_appid.htm).
Автообновление приложения само по себе не появится: первоначально можно
обновлять запуском нового установщика, автообновление — отдельная функция.

Место скачивания: публичная страница/хранилище релизов или публичный GitHub Releases.
Releases приватного репозитория не доступны обычному пользователю без доступа
к репозиторию. Открывать весь репозиторий ради скачивания EXE не нужно.
Установленное приложение использует тот же сервер: это не автономная локальная БД.

## 15. Отделить тестовую разработку

После проверки стабильной версии:

1. По отдельной команде зафиксировать релизный коммит и тег.
2. Настроить защиту `main`, проверки тестов и ручное подтверждение выпуска.
3. Создать `codex/experimental` от проверенного релиза.
4. Продолжать экспериментальную работу там, не на рабочем сервере.
5. Для проверки подготовить отдельный Compose-проект/ВМ, volumes, секреты,
   БД и bucket, а также тестовые домены.
6. Не направлять тестовое приложение на production API и не подключать тестовые
   миграции к рабочей БД. Ветка Git сама по себе не изолирует данные.
7. Проверенные изменения переносить через pull request, тесты, backup и новый
   релиз. На сервере запускать конкретную проверенную версию, не делать
   автоматический `git pull` экспериментальной ветки.

Пример команд ПОСЛЕ согласования и создания релизного тега:

```bash
git switch -c codex/experimental v1.0.0
git push -u origin codex/experimental
```

Если такая ветка уже есть, не пересоздавать и не перезаписывать её.
Откат приложения и откат БД — разные операции: старый образ может быть
несовместим с новой схемой. Поэтому отдельно проверять план восстановления.

## Что предоставить для следующего этапа

- Установлена ли Ubuntu и доступна ли её консоль в VirtualBox.
- RAM/CPU/диск, выделенные ВМ; версии Ubuntu и Docker Compose.
- Выбранный домен и его статус в Cloudflare.
- Нужный лимит сотрудников первой организации.

Не присылать пароли, `.env`, Tunnel-токен, приватные ключи и recovery-коды.
Следующий этап — перенос проверенной версии на вашу ВМ и настройка доменов/Tunnel
по [серверной инструкции](iteration-08/server-deployment.md), затем Windows-установщик.
