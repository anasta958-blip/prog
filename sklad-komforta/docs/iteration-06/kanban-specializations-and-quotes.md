# Специализации канбанов и модель КП/ПКП

## Назначение

Любой канбан остаётся универсальным, пока директор явно не выберет его тип в настройках организации. Для одного канбана допускается ровно одно состояние:

- без специализации — стандартный канбан;
- `КП` — канбан коммерческих предложений;
- `КП + ПКП` — единый канбан коммерческих и предварительных предложений;
- `Комплектация` — канбан комплектаций объекта.

Состояние хранится в `workflows.specialization`, а не в трёх независимых флажках. Поэтому одновременно включить несовместимые типы невозможно ни в интерфейсе, ни через API.

## Интерфейс настройки

Переключатели находятся внутри каждого блока канбана на вкладке `Канбаны`. Они используются и при первичной настройке организации, и при последующем редактировании в пространстве компании.

Повторное нажатие на выбранный переключатель снимает специализацию. Для специализированного канбана дополнительно назначается столбец создания:

- `КП` требует одно действие `Создать КП`;
- `КП + ПКП` требует по одному действию `Создать КП` и `Создать ПКП`; оба действия можно разместить в одном или в разных столбцах;
- `Комплектация` требует одно действие `Создать комплектацию`;
- одно действие нельзя одновременно назначить нескольким столбцам одного канбана.

После выбора специализации обычная кнопка создания карточки во всех столбцах этого канбана скрывается. Это не только правило интерфейса: API стандартного создания карточки также отклоняет запрос для специализированного канбана.

При обновлении существующей организации миграция назначает отсутствующие действия первому столбцу подходящего специализированного канбана. Последующее сохранение настроек записывает выбранные пользователем столбцы и не зависит от этого начального значения.

## Связь с универсальным канбаном

Таблица `kanban_cards` по-прежнему отвечает за номер, колонку, статус, автора и общие поля карточки. Таблица `work_items` задаёт устойчивую идентичность рабочего объекта, а `kanban_cards.work_item_id` связывает его проекции в разных канбанах. Специализированные данные не копируют общие значения:

- `quotes.card_id` связывает КП или ПКП с карточкой;
- составной внешний ключ `(card_id, workflow_id)` запрещает связать предложение с карточкой другого канбана;
- одна карточка может иметь не более одного предложения;
- КП разрешено только для `quote` и `quote_and_prequote`;
- ПКП разрешено только для `quote_and_prequote`;
- тип используемого канбана нельзя сменить на несовместимый.

Эти правила проверяет PostgreSQL, поэтому они одинаковы для Flutter Web, Desktop и мобильных клиентов.

Будущий перенос между КП и комплектацией будет создавать проекцию с новым `kanban_cards.id`, но с тем же `work_item_id`. Данные каждого редактора остаются в своих нормализованных таблицах. Поле, которого нет в целевом канбане, не удаляется и не копируется в неподходящую колонку: оно просто не выводится в целевой проекции и снова доступно после обратного перехода.

Специализированная карточка КП/ПКП не получает техническую товарную категорию: её `kanban_cards.category_id` равен `NULL`. Это поле остаётся обязательным на уровне API только для обычных универсальных карточек. Любое количество реальных категорий конкретного предложения хранится внутри вариантов в `quote_variant_categories`, поэтому категория карточки канбана не подменяет структуру документа.

При переносе в другой специализированный модуль не создаётся вторая полная копия КП. Общая сущность определяется `work_item_id`, а каждый модуль хранит только свою проекцию. Совпадающие данные, необходимые целевому модулю, переносятся в его типизированные поля; исходное КП и его неподдерживаемые целевым модулем данные остаются в таблицах КП. Поэтому связанные записи могут существовать одновременно в таблицах КП и комплектации, но это не две независимые копии одного документа.

## Настройка НДС

Поле `companies.vat_rates` хранит единый список ставок НДС конкретного юридического лица-исполнителя. В карточке юридического лица можно указать несколько значений от 0 до 100, а `null` в списке означает «Без НДС». В КП/ПКП пользователь выбирает ставку только из списка выбранного исполнителя; отдельного набора ставок и отдельного шага компании в рабочей конфигурации нет.

Каждый вариант сохраняет выбранную ставку в `quote_variants.vat_rate`. При смене исполнителя редактор проверяет варианты и заменяет ставку, которой нет в списке нового исполнителя, на первое разрешённое значение. Backend повторяет эту проверку при сохранении и не принимает ставку вне списка юридического лица. Изменение списка ставок не переписывает уже сохранённые предложения автоматически: проверка и возможная замена выполняются только при следующем открытии и сохранении документа.

## Нормализованные таблицы

`quotes` хранит шапку предложения: заказчика, исполнителя, менеджера, РОП, режим выбора и дополнительную информацию.

`quote_proposal_types` хранит типы предложения. Например, один документ может содержать отдельные типы «Кондиционеры» и «Бойлеры».

`quote_variants` хранит варианты внутри типа, подпись и НДС.

`quote_proposal_type_selections` хранит максимум один выбранный вариант для каждого типа предложения.

`quote_variant_categories` и `quote_variant_sections` хранят структуру конкретного варианта. Ссылки на каталог nullable, а снимки названий сохраняются, чтобы последующее переименование каталога не меняло готовый документ.

`quote_positions` хранит позиции. Основные расчётные значения типизированы отдельными колонками, а настраиваемые поля организации размещаются в объекте `values jsonb`.

## Контракты приложения

Файл `SkladKomforta.Application/Quotes/QuoteContracts.cs` описывает коды специализаций и read-модель полного предложения. Он не содержит SQL и не зависит от Flutter, поэтому будет общей границей для последующих endpoint-ов и сервисов КП/ПКП.

## REST API

Специализированные данные доступны внутри адреса карточки канбана:

- `GET /api/v1/kanbans/{boardId}/cards/{cardId}/quote/` загружает полное КП/ПКП;
- `POST /api/v1/kanbans/{boardId}/quotes` атомарно создаёт карточку и первое состояние КП/ПКП в настроенном столбце;
- `PUT /api/v1/kanbans/{boardId}/cards/{cardId}/quote/` создаёт документ либо атомарно заменяет его текущее состояние.
- `GET /api/v1/kanbans/{boardId}/cards/{cardId}/quote/pdf` формирует официальный PDF сохранённого предложения.
- `POST /api/v1/kanbans/{boardId}/cards/{cardId}/quote/client-access` создаёт новую клиентскую ссылку и отзывает предыдущую.
- `GET /api/v1/kanbans/{boardId}/cards/{cardId}/quote/client-access` возвращает состояние активной ссылки без её токена и пароля.
- `DELETE /api/v1/kanbans/{boardId}/cards/{cardId}/quote/client-access` немедленно отзывает ссылку и открытые по ней клиентские сессии.

Чтение требует права `quotes.view`, сохранение — `quotes.manage`. Видимость самой карточки дополнительно проверяется существующей политикой канбана, поэтому право на КП не открывает карточки скрытых сотрудников.

`POST` принимает идентификатор настроенного столбца и полный агрегат документа. Карточка не создаётся при нажатии кнопки: Flutter открывает локальный несохранённый редактор. Только успешное сохранение одной транзакцией создаёт `work_items`, `kanban_cards`, шапку предложения и всё дерево позиций. Ошибка в заказчике, исполнителе, каталоге или любой позиции откатывает транзакцию и не оставляет пустую карточку.

`PUT` принимает весь агрегат существующей карточки. Сначала сервер проверяет UUID, размеры дерева, заказчика, исполнителя, сотрудников и ссылки на каталог. После этого одна транзакция обновляет шапку, синхронизирует название карточки и заменяет дочерние типы, варианты, категории, разделы и позиции. Ошибка в любой строке отменяет всю транзакцию.

Сумму строки клиент не передаёт. Backend выполняет фиксированный порядок: базовая либо ручная цена → наценка → скидка → количество → округление до копеек. Изменение шапки и цен записывается в `audit_log` без копирования произвольного динамического JSON.

Отдельного endpoint удаления предложения нет: удаляется его карточка канбана. Карточка и связанная запись `quotes` помечаются удалёнными в одной транзакции, а действие записывается в аудит. Общая запись `work_items` сохраняется для других проекций рабочего объекта.

## Граница текущего этапа

На этом этапе реализованы выбор специализации, схема хранения, серверная валидация, расчёт, REST API, Flutter-редактор, предпросмотр, печать и защищённая клиентская ссылка КП/ПКП. Одноразовый перенос данных из старого MySQL-дампа выполняется отдельным этапом.

## Flutter-редактор КП/ПКП

Карточка канбана со специализацией `quote` или `quote_and_prequote` открывает полноэкранный редактор внутри рабочего пространства. Боковая навигация приложения остаётся на месте, а обычные канбаны продолжают использовать стандартное модальное редактирование карточки.

Состояние редактора разделено на четыре файла:

- `quote_models.dart` описывает изменяемое дерево документа и локальные сводные расчёты;
- `quote_api.dart` отвечает только за GET/PUT запросы к REST API;
- `quote_controller.dart` загружает справочники, управляет активным типом и вариантом, позициями и сохранением;
- `quote_editor_page.dart` содержит адаптивное представление без SQL и сетевой логики.

Интерфейс повторяет структуру данных `Тип предложения → Вариант → Категория → Раздел → Позиция`. Названия колонок показываются только внутри раскрытого раздела. В шапке раздела доступны массовые наценка и скидка: если строки отмечены, операция применяется к ним, иначе ко всем позициям раздела. На узком экране шапка переносит операции на отдельную горизонтально прокручиваемую строку, а таблица позиций сохраняет полный набор колонок с горизонтальной прокруткой.

Колонки раздела строятся из актуальной настройки полей соответствующей категории каталога. Системные поля редактируют типизированные свойства позиции, пользовательские поля сохраняются в `quote_positions.values`, а справочники предлагают только разрешённые организацией значения. Изменение одной строки обновляет локальное дерево редактора и сводки без повторной загрузки всего предложения.

При выборе карточки каталога редактор загружает её сохранённые зависимости. Каждая связанная карточка добавляется в собственную категорию и раздел текущего варианта. Если такая карточка уже присутствует, новая строка не создаётся: увеличивается только количество на единицу, а введённые пользователем цена, наценка, скидка и остальные значения сохраняются. Эта операция изменяет только затронутые коллекции редактора и не перерисовывает документ через повторное чтение с сервера.

Сводка варианта рассчитывается сразу на клиенте для быстрого отклика, но при сохранении сервер повторно выполняет тот же фиксированный расчёт и остаётся единственным доверенным источником итоговых сумм.

### Предпросмотр

Предпросмотр строится из текущего состояния редактора и поэтому показывает несохранённые изменения без дополнительного запроса к API. Экран выводит реквизиты предложения, типы, варианты, категории, разделы, клиентские цены, скидки и сводки. Закупочные цены в клиентскую таблицу не включаются. На узких экранах документ получает компактные поля и горизонтальную прокрутку широких таблиц без обрезания колонок.

### Печать PDF

Кнопка «Печать» запрашивает PDF сохранённой версии КП/ПКП и предлагает сохранить его на текущем устройстве. При наличии несохранённых изменений печать блокируется явным сообщением, поэтому содержимое файла не расходится с редактором. Сервер повторно проверяет право `quotes.view` и видимость карточки, загружает реквизиты заказчика и исполнителя и формирует чёрно-белый документ A4 с повторяющимися заголовками таблиц и нумерацией страниц. Закупочные цены и внутренняя себестоимость в клиентский PDF не выводятся. Кириллица в Linux-контейнере обеспечивается шрифтом DejaVu Sans, который устанавливается в production-образ API.

### Клиентская ссылка

Кнопка «Ссылка» доступна только для сохранённого предложения без локальных изменений. Диалог показывает наличие активного доступа, срок и последнее открытие, позволяет выбрать срок новой ссылки, отозвать её или перевыпустить. Сервер создаёт случайный токен и отдельный пароль, хранит только их криптографические хеши и отзывает ранее созданную активную ссылку этого предложения. Пароль показывается менеджеру один раз. Срок ссылки ограничен 1–30 днями, клиентская сессия Redis действует не более часа и в любом случае завершается вместе со ссылкой.

Внешний клиент не создаётся в `public.users`, не получает роль, JWT или доступ к пространствам организации. Параметр `quoteAccessToken` открывает отдельный экран ввода пароля вместо штатной авторизации сотрудников. После входа клиент получает только название, исполнителя, клиентские цены, НДС и состав предложения; закупка, маржа и служебные динамические поля отсутствуют в публичном контракте.

В режиме `variant` клиент обязан выбрать ровно один вариант в каждом типе. В режиме `proposal_type` выбирается один тип целиком. Backend проверяет принадлежность всех UUID текущему предложению, сохраняет выбор транзакционно и пишет действие `client_selection_submitted` в аудит. Выбранные клиентом тип или варианты отмечаются в редакторе менеджера. При последующем сохранении неизменённый клиентский выбор сохраняет своё авторство; если менеджер меняет выбранный вариант, новый выбор считается внутренним.

### Выбор позиций и массовые операции

Окно выбора позиции запрашивает только согласованные карточки выбранной категории и раздела. Каждый новый запрос получает собственное поколение: если предыдущий медленный ответ приходит после более нового запроса, контроллер игнорирует его и не показывает товары из другого раздела. При начале поиска старый список очищается, поэтому пользователь не может случайно выбрать устаревшую строку.

После добавления `QuoteController.addCatalogPosition` копирует снимок всех значений карточки каталога в позицию предложения. Затем загружаются связи карточки. Подписи связанных карточек записываются в назначенное поле, а сами связанные позиции добавляются в соответствующие категории и разделы варианта. Любое изменение связанного поля уведомляет интерфейс сразу, даже если новая строка не создавалась.

Чекбокс в заголовке раздела управляет всеми строками этого раздела и показывает три состояния: ничего не выбрано, выбрана часть, выбраны все. Кнопка удаления появляется только при наличии выбранных строк. Массовая наценка и скидка применяются к выбранным строкам; если выбор пуст, значение применяется ко всем строкам раздела.

Ширины колонок сохраняются локально после завершения перетаскивания. Ключ включает идентификатор пользователя из JWT и идентификатор канбана, поэтому настройки разных пользователей и рабочих канбанов не смешиваются. Если суммарная ширина колонок превышает ширину раздела, таблица получает отдельную горизонтальную полосу прокрутки.

### Расчёты и сводки

Клиент и сервер используют одинаковый фиксированный порядок расчёта строки: ручная цена при её наличии, иначе базовая цена; затем наценка, скидка, количество и итоговое округление. Поля каждого этапа выбираются в настройке организации «Правила и расчёты». Для категории без настроенного денежного конвейера действует прежний стандартный расчёт, поэтому существующие КП/ПКП не меняют суммы после обновления. Цена единицы и сумма строки округляются независимо: сумма умножается на количество до округления, поэтому дробные исходные цены не создают расхождений в копейках после сохранения.

Исключённые позиции не входят в суммы раздела, категории и варианта. Сводка типа складывает показатели всех вариантов внутри типа, включая сумму для клиента, закупку, валовую прибыль и НДС. Отрицательная расчётная цена блокирует сохранение ещё на клиенте и повторно проверяется сервером.
