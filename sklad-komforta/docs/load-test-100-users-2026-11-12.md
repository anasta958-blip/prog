# Нагрузочный тест 100 пользователей — 12.11.2026

## Стенд и сценарий

- Публичный адрес: `https://app.eventlab.dpdns.org`.
- VM: Ubuntu, 2 vCPU, около 7,3 ГиБ RAM; Docker: web, API, PostgreSQL, Redis, MinIO, worker, cloudflared.
- Созданы 10 отдельных организаций, 10 директоров и 100 сотрудников. Сотрудникам назначена отдельная тестовая роль со всеми рабочими разрешениями и видимостью всех карточек своей организации. В нагрузке участвовали **100 разных учётных записей**: директор и девять сотрудников каждой организации. Десять остальных сотрудников готовы, но не участвовали одновременно.
- В каждой организации созданы 10 независимых тестовых карточек и 30 товаров. Один пользователь редактировал и перемещал свою карточку. Операции: список канбанов, открытие канбана, список и поиск карточек, открытие карточки, редактирование, переход колонки или изменение порядка, страница и поиск каталога. Между запросами каждого пользователя случайная пауза 0,5–1,5 с.
- Авторизация тестовых аккаунтов выполнена через внутренний API VM, поскольку публичный прокси начал возвращать HTML `429` при массовой первичной настройке. **Вся измеряемая рабочая нагрузка прошла через публичный HTTPS адрес.**
- Сценарий и исходные данные: `benchmark/create_load_users.py`, `benchmark/remote_bootstrap.py`, `benchmark/seed_load_cards.py`, `benchmark/live_distinct_user_stress.py`. Локальный файл `.codex-load-test-credentials.json` содержит пароли и TOTP-секреты, исключён из Git.

## Непрерывные 100 пользователей

Первый трёхминутный повтор дал 109 ответов HTTP 400 на редактировании. Это была ошибка сценария: при повторном запуске он использовал исходную колонку карточки, которую предыдущий прогон уже переместил. Сценарий исправлен: перед нагрузкой он читает актуальную колонку каждой карточки. Первый повтор **не используется** для оценки устойчивости сервера.

Исправленный трёхминутный прогон: **16 617 запросов, 91,6 запроса/с, один `ReadTimeout` после 20 с на редактировании карточки, остальные 16 616 ответов HTTP 200**. Доля неуспешных запросов — около 0,006% (в JSON округлена до 0,01%). В журналах API за последние 10 минут не обнаружены ошибки и исключения; причина единичного таймаута не установлена.

## Большое КП и задержка ввода

В организации `two` сохранено КП №9 с 1200 позициями. Одно чтение и повторное сохранение полного документа без изменения его состава через публичный адрес во время нагрузки заняли:

| Условия | GET, мс | PUT, мс | Результат |
| --- | ---: | ---: | --- |
| Около 25 пользователей | 171 | 852 | HTTP 200 |
| Около 100 пользователей | 411 | 868 | HTTP 200 |

В видимом Edge открыт редактор этого КП. Сценарий `src/flutter/benchmark/live_editor_typing.py` отправлял клавиши в поле количества и измерял задержку до двух `requestAnimationFrame` (по 60 учитываемых вводов). При 100 пользователях p95 составил **53,3 мс** в первом прогоне и **47,6 мс** во втором. Без нагрузки тот же замер дал **56,7 мс**. p95 длительности событий клавиатуры составил 64, 64 и 72 мс соответственно. На всех прогонах наблюдались отдельные длинные кадры из `main.dart.js`; самый долгий скрипт под нагрузкой занял около 234 мс. После каждого прогона документ сохранялся штатной кнопкой.

Эти три коротких браузерных замера не доказывают, что серверная нагрузка увеличивает задержку ввода: контроль без нагрузки оказался хуже второго замера под нагрузкой. При этом цель **менее 50 мс в 95% вводов** на действующем сайте выполняется нестабильно.

## Вывод и ограничения

Стенд обработал 100 одновременно работающих отдельных пользователей с типичным темпом около 92 запросов/с. Основные операции проходили без HTTP-ошибок, но был один 20-секундный таймаут за три минуты. Поэтому утверждать, что задержек совсем не будет, нельзя. Наиболее заметные хвосты задержек — редактирование и поиск карточек; при дальнейшем росте нагрузки сначала следует исследовать PostgreSQL и блокировки операций канбана, а также путь через cloudflared.

Нагрузочный сценарий воспроизводит рабочие HTTP-операции, а не 100 открытых графических браузеров. В новых организациях канбаны стандартные; редактирование КП проверено отдельно на организации `two`. Видеозвонки, загрузка файлов, PDF, массовые импорты, настройка организации и фоновые задачи в этот прогон не входили.

Сырые результаты: `benchmark/live-distinct-100-result.json`, `benchmark/live-distinct-100-sustained-corrected.json`, `benchmark/live-quote-save-result.json`. Файл `benchmark/live-distinct-100-sustained.json` оставлен только для разбора ошибки исходного сценария.
