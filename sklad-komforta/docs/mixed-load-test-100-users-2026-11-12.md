# Смешанная нагрузка: 100 пользователей, 12.11.2026

## Стенд и сценарий

Проверен действующий тестовый сайт `https://app.eventlab.dpdns.org` на Ubuntu VM с 2 vCPU. Участвовали 100 разных учётных записей из 10 отдельных тестовых организаций. Авторизация выполнена через внутренний API, рабочие запросы измерялись через публичный HTTPS адрес.

Роли: 10 директоров меняли расчётные правила, 20 пользователей создавали и редактировали КП, 10 — ПКП, 20 — комплектации, 20 — товары каталога, 20 — карточки канбана. Сценарий включал открытие документов, изменение количества, сохранение, поиск, создание и редактирование товаров, переходы карточек. Между действиями каждого пользователя была случайная пауза 1–3 с. Для каждой организации подготовлены тестовый клиент, каталог, доски и документы. Тестовые данные оставлены на стенде по просьбе пользователя.

## Результаты постепенного роста нагрузки

Каждая ступень длилась около 60 с.

| Одновременных пользователей | Запросов | Запросов/с | Неожиданных ошибок |
| ---: | ---: | ---: | ---: |
| 10 | 305 | 4,9 | 0 |
| 25 | 949 | 15,1 | 0 |
| 50 | 1996 | 31,7 | 0 |
| 100 | 3435 | 54,5 | 6 HTTP 500 (0,175%) |

При 100 пользователях сервер сообщил о шести взаимных блокировках PostgreSQL, SQLSTATE `40P01`. Они совпали с шестью ошибками HTTP 500: три при сохранении правил, две при сохранении КП, одна при сохранении ПКП. При изменении правил возникли 34 ожидаемых конфликта версии расчёта HTTP 409; все обработаны через предварительный расчёт, применение и повторное сохранение. Неразрешённых конфликтов нет.

95-й процентиль времени ответа на ступени 100 пользователей:

| --- | ---: |
| Создание КП | 1,64 с |
| Создание ПКП | 0,51 с |
| Создание комплектации | 3,18 с |
| Сохранение КП | 1,84 с |
| Сохранение ПКП | 1,31 с |
| Сохранение комплектации | 1,11 с |
| Сохранение правила | 2,78 с |
| Создание товара | 1,93 с |
| Поиск каталога | 229 мс |
| Поиск канбана | 393 мс |
| Перемещение карточки | 835 мс |

Короткий отдельный запуск, в котором все 100 пользователей стартовали сразу, дал 22 неожиданные ошибки на 861 запрос (2,56%). В журнале были `40P01` и исчерпание подключений PostgreSQL, SQLSTATE `53300`. У PostgreSQL установлено `max_connections=100`; во время постепенного теста наблюдалось 96 соединений, 87 из них в состоянии idle. Это указывает на недостаточный запас подключений для пикового одновременного старта. Причину конкретных взаимных блокировок требуется разобрать отдельно.

После теста все семь контейнеров работали; web, PostgreSQL, Redis и MinIO показывали статус healthy, нагрузка VM вернулась к обычной.

## Вывод и воспроизведение

Текущая конфигурация не обеспечивает безошибочную работу 100 одновременно активных пользователей в смешанном сценарии. Ступень 50 пользователей прошла без ошибок за минуту, но этот короткий прогон не устанавливает устойчивый предел ёмкости. При 100 пользователях заметны и задержки сохранения документов порядка 1–3 с в p95. Следующие изменения для проверки: уменьшить число одновременно открытых соединений или настроить пул, исследовать порядок блокировок при сохранении документов и конфигурации, затем повторить этот же сценарий.

Скрипт: `benchmark/live_mixed_user_stress.py`. Результаты: `benchmark/live-mixed-ramp-result.json` и `benchmark/live-mixed-smoke-corrected.json`. Настройка тестовых организаций: `benchmark/restore_test_config.py`, `benchmark/configure_load_documents.py`, `benchmark/seed_mixed_documents.py`. Файл с учётными данными `.codex-load-test-credentials.json` исключён из Git. Это проверка HTTP API со 100 аутентифицированными клиентами, а не 100 графических окон браузера; отзывчивость интерфейса под этой смешанной нагрузкой отдельно не измерялась.
