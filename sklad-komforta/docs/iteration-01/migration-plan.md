# План миграции

## Принцип

Старое приложение остаётся рабочим до завершения новой версии. Миграция выполняется одноразовым C# importer-ом из зафиксированного MySQL-дампа в пустую PostgreSQL-базу. Повторный импорт в ту же tenant-схему запрещён; каждый запуск имеет идентификатор, журнал и контрольные суммы.

## Этап 0. Подготовка данных

1. Получить финальный дамп и вычислить SHA-256.
2. Повторить read-only аудит.
3. Сформировать отчёты по mojibake, старым КП, отсутствующим клиентам, пустым ценам и несвязанным позициям.
4. Получить подтверждение по файлу `requires-confirmation.md`.
5. Создать карту `legacy_id -> new_uuid` для каждой сущности.

## Этап 1. Каркас

Создать solution, Flutter workspace, Docker Compose, PostgreSQL, Redis, MinIO и Mailpit. Добавить health checks, конфигурацию через env, миграции `public` и шаблон tenant-схемы. На этом этапе нет бизнес-экранов.

## Этап 2. Авторизация и tenancy

Реализовать пользователей, организацию, onboarding директора, tenant provisioning, JWT/refresh/TOTP, сессии устройств, динамические роли и права. Импортировать четыре текущие учётные записи в одну исходную организацию и перенести политики ролей.

Критерии: backend unit tests, API integration tests и Flutter widget tests; вход, обновление токена, 2FA, выход устройства и проверка tenant isolation.

## Этап 3. Каталог

Перенести категории, разделы, группы, поставщиков, единицы, 3 814 карточек, 785 работ и 3 605 связей. Реализовать новые XLSX-шаблоны. Зафиксировать правила уникальности и авторабот тестами.

## Этап 4. Компания

Перенести профили компании, клиентов, подрядчиков, сотрудников и директора. Реализовать выбор компании по умолчанию и tenant-иерархию сотрудников.

## Этап 5. КП/ПКП

Импортировать только подтверждённые предложения. Нормализовать типы, варианты и позиции; сохранить legacy JSON как контрольный snapshot. Реализовать канбан, расчёты, выбор типа/варианта, перенос ПКП в КП и печать.

## Этап 6. Комплектация

Перенести комплектации и все строки, включая 22 пользовательские строки без `product_name_id`. Реализовать перенос из КП, канбан, счета и локальные черновики.

## Этап 7. Настройки

Реализовать настройку пространств, вкладок, канбанов, полей, категорий, ролей и прав. Добавить версионирование конфигурации организации.

## Этап 8. Документы

Перенести шаблоны и версии после преобразования их layout в новую модель. Реализовать backend PDF, таблицы с корректным разрывом страниц, контейнеры, подписи, QR и источники КП/ПКП.

## Этап 9. Итоговая проверка

- сверить количество строк по каждой сущности;
- сверить контрольные суммы денежных итогов КП/ПКП;
- проверить ссылки товар-работа и tenant FK;
- выполнить полный e2e на Windows и Web;
- затем провести platform QA macOS/Android/iOS;
- сформировать отчёт о непринятых/исключённых данных.

## Стратегия тестов

Каждый модуль считается законченным только после:

1. backend unit tests доменных правил;
2. API integration tests с реальным PostgreSQL/Redis/MinIO в Compose;
3. Flutter widget tests ключевых состояний;
4. migration verification на обезличенной копии данных;
5. e2e добавляются после завершения всех модулей.

## Малые итерации

Рекомендуемый размер одной итерации — одна вертикальная функция: миграция/модель, API, экран, тесты и документация. После зелёных тестов пользователь фиксирует результат в GitHub.
