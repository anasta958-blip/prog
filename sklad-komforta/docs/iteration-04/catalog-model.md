# Модель каталога

## Конфигурация

Каталог использует существующие таблицы:

- `catalog_categories` — категории организации;
- `catalog_sections` — разделы конкретной категории;
- `catalog_groups` — группы конкретного раздела;
- `catalog_category_fields` — выбранные поля карточки и их порядок;
- `dictionary_types`, `dictionary_items` — справочники и значения.

`PostgresCatalogService.GetConfigurationAsync` собирает эти таблицы в один
`CatalogConfiguration`. Название и тип поля берутся из серверного
`OnboardingFieldRegistry`, поэтому клиент не может подменить метаданные поля.

Отображаемое название выбранного поля хранится в `catalog_category_fields.label`
и настраивается отдельно для каждой категории. Технический `field_code` и тип
поля по-прежнему берутся из доверенного `OnboardingFieldRegistry`. Поэтому
переименование не меняет расчёты, валидацию, импорт, справочники и связи карточек.
Внутри одной категории названия не могут повторяться без учёта регистра.
Миграция `0018_catalog_field_labels.sql` заполняет системные названия для ранее
созданных категорий, сохраняя совместимость старых настроек.

Каждая категория обязательно содержит четыре системных поля: `name` (название),
`marking` (маркировка/размер), `unit` (единица измерения) и `base_price` (цена).
Их нельзя удалить ни в первичном мастере, ни в последующей настройке компании;
backend проверяет этот инвариант независимо от Flutter-интерфейса. Остальные
поля выбираются, упорядочиваются и удаляются организацией самостоятельно.
Миграция `0017_ensure_fixed_catalog_fields.sql` дополняет недостающими
системными полями ранее созданные категории, не меняя их остальные настройки.

## Карточка

`catalog_items` хранит:

- `category_id`, `section_id`, `group_id` — проверенную структуру;
- `name`, `marking` — части идентичности товара;
- `normalized_name`, `normalized_marking` — generated-колонки для индекса;
- `status` — `pending` или `approved`;
- `values` — объект JSON с остальными настроенными полями;
- создателя, последнего редактора, даты и данные мягкого удаления.

Составные внешние ключи запрещают сохранить раздел чужой категории или группу
чужого раздела. Частичный уникальный индекс действует только для неудалённых
карточек и следует правилу «группа + наименование + маркировка».

## Валидация

`catalog_category_fields.field_type` хранит тип каждого поля категории.
Системные поля получают неизменяемый тип из серверного реестра. Пользовательское
поле имеет автоматически созданный код `custom_*`, выбранный поддерживаемый тип
и обязательное собственное название; расчётный тип вручную создать нельзя.

`PostgresCatalogService.ValidateAsync` проверяет карточку до записи:

- категория существует и имеет настроенные поля;
- переданы только поля этой категории;
- обязательные поля заполнены;
- значения соответствуют сохранённому и проверенному типу поля;
- calculated-поля не принимаются как пользовательские значения;
- `base_price` больше нуля;
- раздел и группа принадлежат выбранной категории.

`CatalogItemRules` содержит чистые доменные правила нормализации идентичности и
проверки цены. Они не зависят от PostgreSQL или HTTP и покрыты unit-тестами.

## Связи карточек

`catalog_category_dependencies` определяет разрешённые направления связей между
категориями. `catalog_item_relations` хранит конкретные пары карточек:

- `dependency_id` — использованное правило зависимости;
- `target_item_id` — карточка, в которой пользователь настроил связи;
- `source_item_id` — прикреплённая карточка исходной категории;
- `sort_order` — стабильный порядок отображения;
- авторов и даты создания/изменения.

Количество в связи отсутствует. Одна исходная карточка может быть прикреплена к
любому числу целевых карточек. Уникальность запрещает только бессмысленный дубль
одной пары внутри одной целевой карточки. Перед сохранением backend проверяет,
что обе карточки принадлежат категориям выбранной зависимости.

## Аудит

Для `created`, `updated`, `deleted` и `relations_replaced` создаётся запись
`audit_log` с типом сущности `catalog_item`. В `diff` хранится объект с
состояниями `before` и `after`.
Физическое удаление API не выполняет.

## Импорт

XLSX содержит видимую строку русских заголовков и скрытую строку стабильных
кодов. Технический скрытый лист связывает листы книги с UUID категорий. Поля
`relation` и `calculated_money` не импортируются как произвольные значения.

Все строки сначала разбираются и проверяются, затем сохраняются одной
PostgreSQL-транзакцией. В XLSX ID является единственным указателем обновляемой
карточки. Заполненный существующий ID обновляет эту запись, включая перенос в
другую группу; пустой ID создаёт новую карточку. Неизвестный или повторяющийся
ID считается ошибкой и не приводит к неявному созданию.

Правило уникальности базы «группа + нормализованные наименование и маркировка»
продолжает защищать каталог от дублей, но больше не используется для выбора
обновляемой строки импорта. Поставщик и единица измерения в уникальность не
входят. Для каждой строки создаётся аудит `import_created` или `import_updated`.

Видимое поле типа `relation` содержит UUID связанных карточек через `;`.
Импорт проверяет направление зависимости и существование каждого UUID, затем
атомарно заменяет набор `catalog_item_relations` и пишет аудит связей.
