# Проверка соединений и структуры PostgreSQL — 12.11.2026

## Причина лимита и простоя

На тестовой VM PostgreSQL работает с `max_connections=100`, из которых 3 зарезервированы для суперпользователя. Значение не задаётся в `compose.server.yaml`, поэтому используется стандартная настройка PostgreSQL. API и worker имеют по одному отдельному `NpgsqlDataSource`; в их строках подключения не было ограничений пула. Стандарт Npgsql: до 100 физических соединений **на пул**, минимальный размер 0, закрытие свободных соединений после 300 с с проверкой раз в 10 с. Поэтому при пике 100 пользователей наблюдались 96 соединений (87 idle) и ошибки `53300`: два процесса вместе могли запросить больше слотов, чем даёт сервер. `idle` в `pg_stat_activity` означает открытое соединение, ожидающее запрос; это нормальное состояние соединения, возвращённого в пул, а не само по себе доказательство утечки. Позже, вне нагрузки, осталось 5 idle-соединений и 14 процессов в `pg_stat_activity` всего, что согласуется с очисткой пула.

В `compose.server.yaml` заданы пределы 60 соединений для API и 8 для worker, время простоя 60 с и проверка раз в 10 с. Максимум приложений на этой VM теперь 68, оставлен запас для административных подключений. Серверный `idle_session_timeout` намеренно не включён: он может обрывать соединения, которые приложение держит в пуле. Увеличение `max_connections` само по себе не устраняет взаимные блокировки и увеличивает нагрузку на PostgreSQL.

При чтении КП и комплектации проверка прав раньше открывала дополнительное соединение, пока соединение документа уже было занято. Порядок операций изменён: проверка прав завершается до открытия соединения документа.

## Взаимные блокировки

Шесть ошибок `40P01` при 100 смешанных пользователях совпали с сохранением правил и предложений. Изучение `PostgresCompanyService.UpdateConfigurationAsync` показало, что при сохранении только правил транзакция повторно записывала неизменённые словари, категории, поля и канбаны. Это создаёт лишние блокировки на таблицах, с которыми работают документы. Код теперь сравнивает материальную часть конфигурации и пропускает её синхронизацию, если менялись только правила или иные поля черновика. Это устраняет установленный источник лишних блокировок; для доказательства исчезновения всех `40P01` нужен повторный нагрузочный тест после развёртывания.

## Структура базы

В крупнейшей организации на момент проверки около 4400 товаров, 2500 позиций КП и 1200 позиций комплектаций. На внешних ключах `quote_positions.catalog_item_id` и `order_positions.catalog_item_id` не было индексов. Миграция `0052_document_catalog_reference_indexes.sql` добавляет частичные индексы по ненулевым ссылкам, чтобы удаление товара или изменение его идентификатора не заставляло PostgreSQL искать связанные позиции полным сканированием. Обзор других отсутствующих индексов внешних ключей не доказывает, что все они нужны: для малых таблиц лишние индексы только увеличат стоимость записи.

Проверки: YAML конфигурации разобран, проект собран, `dotnet test SkladKomforta.sln --no-restore` — 327 тестов пройдены, 8 тестов с реальной базой пропущены из-за отсутствия локального подключения. Изменения пока находятся в рабочей копии; сервер продолжает работать со старой сборкой.
