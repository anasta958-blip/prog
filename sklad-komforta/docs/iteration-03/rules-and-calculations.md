# Правила и расчёты

## Назначение

Вкладка «Правила и расчёты» находится после вкладки «Поля» и используется как
при первичной настройке организации, так и при последующем редактировании её
конфигурации. Редактор не создаёт системные поля: пользователь связывает правила
только с полями, которые уже добавлены в соответствующую категорию.

Конфигурация хранится вместе с остальным черновиком организации в JSONB-поле
`onboarding_draft.payload`. Это сохраняет атомарность: незавершённые изменения не
попадают в рабочую конфигурацию до сохранения всего черновика.

## Денежный конвейер

Для каждой категории можно настроить несколько денежных конвейеров. Каждый
конвейер имеет собственный устойчивый идентификатор и записывает результат в
отдельное поле. Два конвейера одной категории не могут записывать результат в
одно и то же поле. Порядок операций задан системой и не переставляется
пользователем:

1. Базовая цена.
2. Ручная цена, если она заполнена.
3. Наценка.
4. Скидка.
5. Количество.
6. Округление.
7. Запись результата.

Пользователь выбирает существующие поля базовой и ручной цены, наценки, скидки,
количества и результата, точность округления и участие результата в общих
итогах. Backend повторно проверяет тип каждого выбранного поля.

`RuleCalculationEngine.CalculateMoneyPipeline` выполняет расчёт в едином порядке.
В редакторе КП/ПКП его вызывает `QuoteConfiguredCalculationEngine`: Flutter
пересчитывает строку сразу после изменения для быстрого отображения, а backend
повторяет расчёт перед сохранением и остаётся доверенным источником результата.
Ручная цена заменяет базовую только при наличии значения; количество по умолчанию
равно единице. Если для категории не настроен ни один конвейер, сохраняется
обратно совместимый стандартный расчёт строки.

Каждый конвейер можно независимо включить или исключить из сводных итогов.
Несколько включённых конвейеров одной категории складываются, а результат
отключённого конвейера остаётся в назначенном поле, но не увеличивает сумму
позиции и варианта.

## Событийные правила

Правило принадлежит одной категории и содержит событие, ноль или несколько
условий и хотя бы одно действие.

Поддерживаемые события:

- изменение выбранного поля;
- сохранение карточки;
- расчёт строки;
- расчёт варианта.

Поддерживаемые условия:

- флажок включён или выключен;
- числовое значение больше нуля;
- поле заполнено;
- значение равно указанному.

Поддерживаемые действия:

- исключить строку из итогов;
- записать значение в другое поле;
- рассчитать поле по формуле;
- добавить или удалить связанные карточки;
- показать или скрыть поле;
- запретить сохранение с заданным сообщением;
- прибавить или вычесть денежное поле из итога варианта.

Действия со связанными карточками принимают только зависимость, которая была
настроена для выбранной категории. Денежная агрегация принимает только денежные
поля и при необходимости может учитывать выбранное поле количества.

В текущем runtime КП/ПКП исполняются расчётные действия `exclude_row`,
`set_field`, `calculate_field`, `block_save` и `aggregate_money`. Действия
`add_related_cards`, `remove_related_cards` и `set_field_visibility` относятся к
поведению интерфейса и зависимостей карточек; они хранятся и валидируются, но не
подменяются денежным движком фиктивной реализацией.

## Формулы

Формула собирается визуально из существующих числовых полей, числовых констант,
скобок и операций сложения, вычитания, умножения и деления. В базе хранится
структурированный список токенов, а не программный код.

Backend проверяет порядок операндов, допустимые типы полей, баланс скобок,
точность округления и деление на ноль. `RuleCalculationEngine.CalculateFormula`
использует обычный приоритет операций и никогда не исполняет JavaScript, Dart,
C# или произвольные выражения пользователя.

## Основные модели

- `CalculationRuleDraft` — правило, категория, событие, условия и действия.
- `RuleConditionDraft` — одно условие выполнения.
- `RuleActionDraft` — одно разрешённое действие.
- `FormulaDraft` и `FormulaTokenDraft` — безопасное представление формулы.
- `MoneyPipelineDraft` — именованное сопоставление полей одного фиксированного
  денежного расчёта; несколько записей могут принадлежать одной категории.

Flutter-модели имеют обратно совместимые `fromJson`: старые черновики без `rules`
и `moneyPipelines` загружаются с пустыми списками.

Материализованная таблица `catalog_categories` хранит `client_id` категории.
UUID используется внешними ключами рабочих данных, а `client_id` связывает
категорию с правилами в `onboarding_draft.payload`. Миграция
`tenant/0032_catalog_category_client_id.sql` восстанавливает этот идентификатор
для существующих организаций и делает его уникальным, поэтому переименование и
изменение порядка категорий не переназначает расчёты.

## Проверки

- backend unit-тесты проверяют типы полей, незавершённые формулы, порядок
  наценки и скидки, скобки, приоритет операций, денежную агрегацию, исключение
  конвейера из итогов и запрет сохранения правилом;
- Flutter unit-тесты проверяют JSON-сериализацию, совместимость старых
  черновиков и совпадение динамического пересчёта со сводкой документа;
- Flutter widget-тесты продолжают проверять общий редактор настройки.

Миграция `tenant/0020_onboarding_rules_and_calculations.sql` расширяет допустимый
номер шага до девяти. Отдельных таблиц и удаления существующих данных нет.
### Выполнение правил в редакторе предложений

- `set_field_visibility` применяется к конкретной строке и не меняет ширину или порядок колонок соседних строк.
- `add_related_cards` загружает сохранённые связи карточки каталога и добавляет каждую связанную карточку один раз для конкретной исходной строки.
- `remove_related_cards` удаляет только автоматический вклад соответствующей исходной строки и зависимости. Ручное количество и ручные строки не удаляются.
- Для сопоставления правила с материализованной зависимостью используется стабильный `client_id`, а не UUID, который может измениться после повторного сохранения конфигурации.
- Правила события `field_changed` выполняются последовательно, поэтому быстрые изменения одного поля не создают дубли связанных строк.
- Для `highlight_field` в `quote_positions.values._active_highlight_rules` сохраняются только `client_id` сработавших правил. При повторном открытии подсветка восстанавливается из действующих правил; цвет и сообщение берутся из текущей конфигурации. Отключённые правила и правила с переставшим выполняться условием удаляются из состояния строки.
