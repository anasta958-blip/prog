# Итерация 3. Авторизация и multi-tenant

## Цель

Итерация реализует безопасный первый вертикальный модуль новой системы:
учётные записи без публичной регистрации, первичную смену пароля, TOTP,
refresh-сессии устройств, создание организации и изолированной tenant-схемы.

## Согласованное визуальное направление

Для экранов авторизации выбран вариант 1 из
[сравнительного листа](authentication-design-options.png): графитовая основа,
холодный синий акцент, строгая сетка и спокойная двухпанельная композиция на
широких экранах. На мобильных устройствах второстепенная панель сворачивается,
а основной сценарий остаётся доступен без горизонтальной прокрутки.

Это решение включает не только цвета, но и правила компоновки:

- компактная форма располагается в отдельной рабочей области;
- объяснение шага и состояние безопасности отделены от полей ввода;
- шаги первого входа показываются единым последовательным сценарием;
- ошибки выводятся рядом с причиной и содержат способ восстановления;
- основные действия имеют один синий акцент, опасные действия используют
  отдельный красный статус;
- desktop и mobile используют одну логику, но различную адаптивную композицию.

## Правило следующих дизайн-вариантов

Следующие три варианта каждого нового экрана должны отличаться архитектурой
интерфейса, а не только палитрой. Сравниваются, например:

- боковая навигация против верхней или контекстной;
- таблица против карточек или иерархического дерева;
- мастер по шагам против одного составного экрана;
- постоянная панель свойств против модального или встроенного редактирования;
- разные приоритеты информации и сценарии для desktop/mobile.

Простая перекраска одной и той же разметки отдельным вариантом не считается.

## Текущее состояние

- добавлена public-миграция `0002_identity_security`;
- добавлена tenant-миграция `0002_identity_authorization`;
- добавлены серверные правила пароля и RFC 6238 TOTP;
- новая public-миграция применена к тестовой PostgreSQL;
- реализованы ротация refresh-токенов и отдельные сроки жизни Web/native;
- Web хранит refresh-токен только в `HttpOnly` cookie, нативные клиенты — в
  системном secure storage;
- реализованы активные сессии, отзыв устройства, выход и recovery-коды;
- создание первой организации поднимает отдельную PostgreSQL-схему;
- выбран и реализован вариант 2 семишаговой настройки организации;
- незавершённый прогресс хранится на сервере и материализуется только при
  финальной активации;
- каждый tenant-запрос проверяет активность пользователя, сессии, организации
  и членства до установки `search_path`;
- роли, права и их назначения хранятся внутри tenant-схемы;
- системные роли директора и администратора имеют `system.full_access`;
- добавлен адаптивный Flutter-сценарий входа для всех целевых платформ;
- доменные, API integration и Flutter widget-тесты проходят полностью.
